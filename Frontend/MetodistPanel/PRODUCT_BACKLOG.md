# Бэклог пользовательского пути методиста

Общий рабочий файл автоматизаций менеджера, разработчика и сверки результатов из других чатов. Продуктовый менеджер обновляет задачи на основании кода, контрактов API и проверяемых сценариев. Фронтенд-разработчик берёт одну небольшую задачу со статусом `READY`, реализует и фиксирует результат проверки. Сверка учитывает завершённую работу из других чатов только после проверки кода и результата тестов. Не удалять историю выполненных задач и не перезаписывать чужие правки.

## Путь и приоритет

Регистрация → вход → создание музея → создание артефакта → публикация → открытие опубликованного артефакта в Visitor. Ошибки и пустые состояния на этих шагах важнее косметики. Удаление легаси и сверка с бекендом выполняются там, где они влияют на этот путь или мешают его безопасному развитию.

## Правила для задач

- Статусы: `READY`, `IN_PROGRESS`, `BLOCKED`, `DONE`.
- В каждой задаче нужны: проблема и пользовательский эффект, ссылки на доказательства в репозитории, объём изменения, критерии приёмки, необходимые unit-тесты, риск и зависимости.
- `READY` означает, что задачу можно выполнить на фронтенде по подтверждённому контракту. Неясный контракт или потребность в изменении бекенда означает `BLOCKED` с конкретным вопросом.
- Менеджер добавляет и уточняет задачи, удаляет дубликаты, отмечает зависимость и приоритет. Он не меняет код приложения и не меняет статус `IN_PROGRESS` или `DONE` без подтверждённых оснований.
- Разработчик перед изменением сверяет Git и актуальный контракт, отмечает задачу `IN_PROGRESS`, делает один безопасный срез, добавляет осмысленные unit-тесты, выполняет тесты, lint, typecheck и build, затем отмечает `DONE` или `BLOCKED` с результатом и остаточным риском. Не публикует и не развёртывает сайт.
- До закрытия задачи проверить соответствующий пользовательский сценарий; если браузерная или серверная проверка недоступна, явно записать ограничение.

### MP-003 · P1 · Сохранять текст экрана при отказе API

- **Статус:** DONE; выполнено 2026-10-17. Подтверждённый дефект участка «создание артефакта → публикация» для методиста с доступом к музею.

Успех нельзя определять по закрытию редактора.
- **Объём:** только фронтенд: явный результат асинхронного сохранения экрана, закрытие редактора после подтверждённого успеха; при ошибке сохранить введённые поля и дать повторить. На время запроса исключить повторную отправку и переход к публикации, который размонтирует редактор. Не расширять задачу до общей защиты всех переходов и не менять контракт API.
- **Приёмка:** пока PATCH и обновление данных не завершены, редактор открыт, сохранение показывает ожидание, повторный клик не отправляет второй PATCH. При успехе PATCH и отказе последующего GET редактор сохраняет ввод, не сообщает об успешном завершении; после восстановления сервиса повтор позволяет завершить сохранение. Во время ожидания переход к публикации недоступен.

Проверить связь результата сохранения с закрытием редактора, а не только чистую функцию классификации. При необходимости добавить минимальную инфраструктуру компонентного теста; существующие npm test для профиля должны проходить.
- **Риски и зависимости:** не сбросить поля эффектом инициализации при обновлении screen, не спутать сохранение с загрузкой изображения. При сбое GET после PATCH данные могли уже сохраниться на сервере; повтор PATCH может увеличить draft revision — нельзя обещать откат или повторять запрос автоматически. Бекенд менять не требуется; MP-002 блокирует сквозной прогон нового пользователя, но не реализацию и тестирование этого среза с подменённым API.

MP-001 сохранена DONE; npm test повторно прошёл 4/4, текущие тесты покрывают переходы состояния профиля, а не полноценную работу UI и API. - **Результат:** сохранение экрана возвращает явный успех; редактор закрывается только после PATCH и успешного обновления списка экранов.
