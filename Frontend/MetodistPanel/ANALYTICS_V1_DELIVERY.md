# Аналитика v1 — решения и очередь реализации

17 октября 2026. Пользователь поручил зафиксировать первую рабочую версию и разделить реализацию после продуктового анализа. Родительское требование MP-006 и серверный объём MP-007 сохраняются; первая версия не закрывает весь будущий функционал маршрутов, команд и рейтинга.

## Зафиксированные решения

| Вопрос | Решение для v1 | Что не входит в v1 |
|---|---|---|
| D1. Кого считаем | Уникальный visitor_key браузера в музейном контексте, согласно METRICS.md; подпись объясняет, что это цифровая аудитория | Признание ключа физическим человеком, объединение устройств/аккаунтов без проверенной связи |
| D2. Просмотры и завершение | scene_view — уникальный экран в сессии; scene_complete — достижение финального экрана; active_minutes — сумма времени видимости | Переименование screen_views в открытия артефактов; трактовка финала как полного прочтения или завершения маршрута |
| D3. Маршруты и команды | Отдельные источники будущего этапа; контролы и неподдержанные вкладки явно недоступны с причиной | Игнорирование route_id/team_id, имитация фильтра, вывод маршрута из одной истории |
| D4. Коллекции и другие источники | Использовать реальные collection rows, если настроен источник; partial error при collection_source_unavailable. Недавняя активность главной — активность посетителей с соответствующей подписью | Подмена коллекции favorite; смешивание событий Visitor с журналом действий методиста. Feedback/rating остаются недоступны |
| D5. Время и сравнение | Текущая семантика backend: [from,to), календарный period, UTC по умолчанию с явным указанием; delta — процент к предыдущему календарному периоду, при предыдущем 0 — null | Молчаливый перевод в timezone устройства; новое сравнение на одинаковую прошедшую часть месяца; дробление day на часы без backend поддержки |
| D6. Состав поставки | Только поддерживаемые метрики, честные ошибки и фильтры. Неизвестные метрики не заменяются нулями/демо; подконтрольные несовпадения подписей исправляются на фронтенде | Публикация всех семи вкладок как полностью готовых при одинаковых серверных данных и неподключённых источниках |

Это рабочие продуктовые решения на основе существующего v1, а не переписывание OpenAPI или согласование несуществующего сервиса. Изменения серверной семантики из исходного анализа (cohort completion, account linking, hourly buckets, export endpoint) остаются расширениями, не блокирующими правдивую выдачу уже имеющихся данных.

## Актуализация после продуктового анализа

Рабочее дерево меняется параллельно. Повторно сверены `Backend/analytics-service/main.go`, `METRICS.md`, `openapi.yaml`, `Backend/dashboard-service/main.go`, `Frontend/MetodistPanel/src/api.js`, VisitorsView и useStatsData.

- Collection integration уже появилась: list получает collected_artifacts из artifacts database; сортировка collectedArtifacts поддержана. Ошибка источника возвращает 503 collection_source_unavailable. Проверять конфигурацию отдельно от кода.
- Content/stories/artifacts summary теперь отдаёт scene_views, story_completions и active_minutes; artifacts также collections. Это счётчики экранов, финалов и сумма минут, а не среднее/проценты.
- Breakdown теперь «Типы событий», bars — «Экспонаты по просмотрам». Их нельзя показывать под старыми заголовками «Устройства» или «Источники». Рейтинг использует названия из данных событий.
- Dashboard recent-activity проецирует visitor events. Рейтинг, маршруты и команды всё ещё не имеют подтверждённых источников.
- API-клиент уже использует sessionAuthHeaders для dashboard/analytics: не ставить повторную задачу на добавление того же заголовка.
- Историческая матрица PRODUCT_ANALYTICS_ANALYSIS.md описывает предыдущий снимок. Этот раздел уточняет появившуюся реализацию, не подтверждает её запуск на стенде. Предыдущие 503 и отсутствие авторизованного browser smoke остаются ограничением проверки.

Routes/feedback/rating unavailable. Новая задача на этот объём не дублирует DONE |
| Посетители | Три подтверждённые KPI, два независимо загружаемых ряда, sources, серверная таблица с id и коллекциями при доступности источника | period day/week/month/year применяется ко всем блокам; серверная пагинация/поддержанные сортировки. Фиктивная дата удалена; произвольный диапазон/route/team явно недоступны до следующего среза. CSV явно «текущая страница» |

## Два ближайших фронтенд-среза

1. **MP-008 READY P1 — «Посетители»: реальные данные, единый период и серверная таблица.** Одна страница, существующие endpoints, без новых серверных полей. Основной пользовательский результат: период меняет реальные запросы, числа и список соответствуют одному диапазону, отказ не превращается в демо.
2. **MP-009 READY P1 — «Статистика»: серверные блоки без выдуманных значений.** Одна data/view цепочка на существующих tab/view, правильные подписи и состояния, общий period, защита от старых ответов. Не требует MP-008 и не меняет backend.

Это единственные две новые задачи в текущем запуске. Нет задачи IN_PROGRESS до фактического начала исполнителем. Разработчик по правилам общей очереди берёт одну READY; пользователя не подписывают на другую переписку и не отправляют сообщения в другие чаты без поручения.

## Следующие срезы после этих задач

| Порядок | Ограниченный объём | Зависимость и критерий создания READY |
|---|---|---|
| 3 | Явный календарный диапазон на «Посетителях» | MP-008; existing from/to/timezone contract, общий query всех блоков; убрать period при from/to; unit границ/DST и reset page |
| 4 | Выбор period графика главной и объяснение monthly summary | Сохранить DONE MP-005; attendance поддерживает period. Отдельно тестировать, что monthly карточка не становится недельной |
| 5 | Разбиение секций статистики по устойчивым ключам и запросам | MP-009; согласованный mapping нескольких rankings/bars, не первое/последнее lowerSections; не нужны новые фиктивные dimensions |
| 6 | Полный экспорт посетителей | Должен появиться серверный экспорт/согласованный snapshot обхода всех страниц; до этого только явно обозначенный page CSV |
| 7 | Наблюдаемость покрытия и проверка источника на стенде | Владелец окружения: authenticated smoke и Visitor event → DB → GET → UI; data_started_at/watermark требуют подтверждения backend |
| 8 | Route/team/feedback/rating и дополнительные формулы | MP-007: реальные каталоги/факты, схемы ответа и тесты до создания READY для панельного подключения |

Пункты 3–8 — порядок дальнейшего разбиения, не скрытые READY-задачи и не выполненная работа. Их оформлять небольшими карточками после проверки текущего кода, не более двух за запуск и не более пяти READY одновременно. Полное исходное требование остаётся открытым, пока эти возможности не реализованы либо их исключение явно принято пользователем.

## Проверка готовности первой версии

- MP-008/MP-009 проходят unit на actual request/navigation handlers, затем lint/typecheck/build и согласованный browser/API smoke. Моки проверяют UI, но не доказывают поступление данных Visitor.
- Контрольный набор из раздела 10 PRODUCT_ANALYTICS_ANALYSIS.md проверяет unique=2,new=1,3 sessions,avg_active=1.5 минуты,3 screen_views и 2 открытия только если сервер реализовал отдельную метрику opens. Отсутствующие opens не нужно рассчитывать на фронтенде из суммы экранов.
- Два музея изолированы; period совпадает в meta всех блоков; table total учитывает >50 строк. Нулевые/пустые ответы, null, 401, 503 и stale response проверяются отдельно.
- Collections=1 в тестовом диапазоне только при реально подключённом источнике; retry сохраняет первую дату. Для offline Visitor результат оценивается после подтверждённой записи события, не по sendBeacon return value.
- Первая версия не считается работающей на 192.168.31.125 по одному наличию файлов, HTML-отчёта или успешного build. Развёртывание/перезапуск не входят в эту продуктовую постановку.
