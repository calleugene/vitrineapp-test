## 1. Вывод и границы проверки

Задача — дать методисту ответ на три вопроса: сколько людей пользуется цифровым музеем, какой контент помогает им пройти историю и где нужно улучшение. Цифры должны иметь единый смысл на трёх страницах и воспроизводиться из серверных фактов при одинаковых фильтрах.

Факты текущей проверки:

- `http://192.168.31.125/methodist/visitors` в доступной браузерной сессии показывает вход. Авторизованный UI не проверен. Состав блоков ниже установлен по текущему исходному коду, а не по скриншоту после входа.
- Read-only GET `/api/analytics/healthz`, `/api/dashboard/healthz`, `/api/analytics/api/v1/visitors/summary`, `/api/dashboard/api/v1/dashboard/summary` на этом хосте вернули 503. Эти проверки без авторизации подтверждают недоступность данных через стенд, но не конкретную причину и не корректность защищённого чтения.
- В рабочем дереве уже есть `Backend/analytics-service` с OpenAPI, METRICS.md, SQL и тестами; `Backend/dashboard-service` проецирует analytics. Старое утверждение об отсутствии этих каталогов больше не актуально. Их изменения незакоммичены; это не доказательство развёртывания.
- `go test ./...` в analytics-service прошёл (cached); в dashboard-service завершился успешно с `[no test files]`. Это не сквозная проверка стенда.
- MP-005 уже DONE: главная разделяет состояния и не подставляет демо; изменение сохраняется. В «Посетителях» и «Статистике» демо-fallback остаётся.

Ниже **«есть в коде»** означает реализацию, проверенную чтением файлов. **«требуется»** — предложение к контракту/реализации, которое нельзя считать уже работающим. Спецификация не изменяет код и не принимает решения о развёртывании.

## 2. Источники и ответственность

| Источник | Что является фактом | Что он не подтверждает |
|---|---|---|
| analytics-service: `analytics_events` | Принятые visit_start, scan, scene_view, engagement, scene_complete, quiz_answer с event time и museum scope | Физическую посещаемость музея, реальное ФИО, платёж/билет, успешный collect, прохождение маршрута |
| artifacts-service: публичный snapshot | Принадлежность музею, артефакт, опубликованные экраны; источник названия/категории и версии | Историческую классификацию после редактирования без сохранения версии/измерений |
| artifacts-service: persisted collect | Подтверждённое добавление в коллекцию | Количество нажатий кнопки, просмотр или избранное |
| visitor-service + auth-service | Гостевая/аккаунтная идентичность, разрешённая привязка гостя; права методиста | Автоматическое совпадение с отдельным analytics visitor_key |
| Каталог маршрутов + серверный факт route run | Состав/версия, старт, прогресс, завершение маршрута | Этих данных пока нет в analytics; наличие route_id в клиентском коде недостаточно |
| Каталог команд/участие в команде | team_id, разрешённое участие, сегмент при наличии явного справочника | Нельзя вывести «семья» или «школьная группа» из устройства/поведения |
| Feedback source | Сообщение, тип, статус, оценка, даты поступления/первого ответа | События чтения истории не порождают оценки или отзывы |
| Журнал операций контента | Создание, редактирование, публикация, архивирование с actor/time/entity | Не равен журналу посещений Visitor |

analytics-service владеет расчётами и дедупликацией. dashboard-service переиспользует расчёты, а не считает «посетителей» второй формулой. Панель управляет фильтрами, форматированием и состояниями. Visitor сообщает события автоматически, не показывает посетителю технические ошибки аналитики.

Поток данных: **Visitor → POST analytics/events → проверка опубликованного объекта → analytics_events → общий расчёт → analytics GET / dashboard projection → панель**. Collect/маршрут/feedback входят как отдельные серверные факты, а не как доверенные браузерные клики.

## 3. Словарь метрик

Существующая аналитика считает псевдонимы браузеров. До проверенной привязки аккаунта подпись/tooltip должны говорить «уникальные браузерные посетители»; это не количество физических посетителей. Очистка хранилища и другое устройство дают другой ключ. Воронка начинается с успешного показа опубликованного контента, а не с GET HTML, камеры или экрана входа.

| Код | Определение и единица | Источник / состояние |
|---|---|---|
| unique_visitors | DISTINCT visitor_key в музее за [from,to) | Есть как total_visitors; сейчас учитывается любое принятое событие. Сохранить это правило в v1 и указать границу покрытия |
| new_visitors | Посетители из выбранного множества, чей первый известный event в этом музее попал в интервал | Есть. «Новые с начала сбора», не доказательство первого физического визита |
| returning_visitors / returning_rate | first_seen < from; доля = returning / unique × 100 | Требуется явное поле; не путать с повторной сессией нового посетителя в том же интервале |
| sessions | DISTINCT (museum, visitor_key, session_id), сессия после 30 минут неактивности | Сейчас session_id генерируется Visitor, среднее считает DISTINCT session_id. Утвердить состав ключа и поведение нескольких вкладок |
| avg_active_session_minutes | SUM подтверждённых active_ms / sessions / 60000, для событий выбранного интервала | Есть как avg_session_minutes; это активное время истории, не время на маршруте и не длительность открытой вкладки |
| screen_views | Количество принятых scene_view; в текущем v1 один screen на (museum,session,artifact,screen) | Есть. Это дедуплицированные просмотры экранов, повторный показ в той же сессии не добавляется |
| artifact_opens | DISTINCT (museum,visitor,session,artifact) с первым scene_view в этом посещении | Требуется отдельная агрегация. Не равно SUM screen_views; название «просмотры артефактов» без определения запрещено |
| story_completion_rate | Завершённые story runs / открытые story runs одной когорты × 100 | Пока есть событие final screen, но нет согласованной run/cohort модели. «Достигли финального экрана» не доказывает просмотра всех экранов |
| avg_story_active_minutes | Активное время / количество открытых story runs той же когорты | Требуется явная модель; не использовать avg_session_minutes |
| avg_screen_depth | SUM уникальных показанных экранов по сессиям / sessions выбранного интервала | Требуется отдельное поле; единица «экранов/сессию», не процент completion |
| favorites_added | Новые подтверждённые переходы favorite=false → true в интервале | Отдельно от collect; нужен серверный факт изменения, retry не добавляет второй факт |
| share_actions | Успешные вызовы share/copy action, по определённому событию | Пока нет источника; не означает состоявшуюся пересылку или прочтение получателем |
| qr_entries | Успешные входы с source=qr, а не физически доказанные сканирования | Сигнал есть. Старые QR без метки попадают в direct; URL можно переслать. Tooltip обязан отражать ограничение |
| collected_artifacts | Количество новых persisted collect фактов в интервале; unique по visitor+artifact | Интеграция отсутствует. Повтор collect и retry не увеличивают счётчик; total collection на текущую дату — другая метрика |
| route_starts / completions | Подтверждённые route_run по версии маршрута | Нет источника. Финал одной истории не равен завершению маршрута |
| route_completion_rate | Завершённые runs / стартовавшие runs одной когорты | Требуется определить окно наблюдения. Текущий месяц ещё не завершён: показать provisional и as_of |
| avg_route_duration_minutes | Сумма подтверждённого активного времени route runs / соответствующие runs | Нет источника; отдельно согласовать all-started или completed-only и явно подписать |
| avg_route_progress_percent | Среднее по runs: выполненные обязательные шаги / обязательные шаги версии × 100 | Нет источника. Не подменять долей экранов всех посетителей или общим completion rate |
| museum_rating | SUM eligible ratings / eligible ratings count, диапазон и шкала из источника | Нет источника. Не усреднять уже усреднённые оценки маршрутов без весов |

Если знаменатель отсутствует, среднее/доля — `null`, а не доказанный 0. Текущий backend возвращает avg_session_minutes=0 и при отсутствии сессий: это отдельное расхождение с предлагаемым продуктовым правилом. Ноль количества при работающем сборе — валиден; отсутствие источника, неработающий сбор или неполное покрытие — отдельные состояния.

Текущий engagement измеряет видимость экрана, а не подтверждённое внимание: видимый, но оставленный без действий экран тоже может добавлять время. Подпись v1 — «активное время при открытой истории» с tooltip; улучшение idle detection требует отдельного согласованного правила.

Продуктовое предложение: сохранить у карточки «за месяц» фиксированный месяц, пока контракт это явно подразумевает. График может иметь самостоятельный период с собственным заголовком; не создавать впечатление, что он фильтрует карточки. Следующим согласованным изменением можно сделать глобальный диапазон главной, но тогда изменить название/поле monthly card совместимо. Нельзя уже сейчас обещать, что `/dashboard/summary?period=week` вернёт недельную сводку.

## 6. Статистика: матрица семи вкладок

Общая форма маршрутов есть: GET `/stats/{tab}/summary|chart|breakdown|ranked|bars`. Наличие общего обработчика не означает, что каждая комбинация возвращает нужный бизнес-результат.

| tab | Карточки: целевой смысл | График | Разрез / рейтинги / нижние блоки | Доступность и источник |
|---|---|---|---|---|
| overview | unique_visitors, screen_views, avg_active_session_minutes, museum_rating | unique_visitors по времени | sources по visitor; TOP routes; TOP artifacts/story; device_class | Сейчас summary даёт только visitors, chart — visitors, ranked — artifact IDs по screen_views; breakdown/bars=503. Rating/routes/device source не подключены |
| visitors | unique, new, avg_active_session_minutes, returning_rate | unique и/или new по времени | sources; маршруты привлечения; явно определённые сегменты | Можно переиспользовать visitors summary/dynamics/sources; сейчас stats summary только visitors, а ranked вообще артефакты. Семьи/школьники не выводим без источника |
| content | screen_views, completion_rate, avg_screen_depth, favorites_added | screen_views | Категории объектов, TOP stories, TOP artifacts; распределение просмотров по типам экранов | Все четыре карточки есть в макете, backend summary даёт только scene_views. Completion требует run/cohort; favorites — отдельного серверного факта. Типы экранов в событиях/исторических измерениях не сохранены |
| routes | route_starts, completions, completion_rate, avg_route_duration_minutes | route_starts | route category; TOP routes; exit step; entry source | Все запросы сейчас 503; нужны route run и версия маршрута. Доля выходов: знаменатель runs, не посетители |
| stories | artifact_opens (story=artifact в v1), completion_rate, avg_story_active_minutes, share_actions | story opens | Категории; TOP stories; устройства; действия после чтения | Сейчас summary/chart показывают просмотры экранов, не открытия историй. Шеринг/копирование не собираются; нельзя назвать share click доказанной пересылкой |
| artifacts | artifact_opens, qr_entries, new_collects, avg_artifact_active_minutes | artifact opens | artifact category; TOP artifacts; экранные форматы; entry source | Сейчас только screen_views, scan events есть, коллекции не связаны. Любое «сохранение» явно различать с favorite/collect |
| feedback | messages, reviews, questions, avg_rating | created messages | type; subjects; first-response buckets; channel | Все запросы 503; нужны сообщения, статусы, каналы и first_reply_at. Нельзя выводить SLA из событий Visitor |

Макет хранит до трёх lowerSections, но `stats/views.jsx` и hook отображают только ranked и последний bars. В результате промежуточные рейтинги/«точки выхода»/«формат чтения» могут вообще не попасть в UI. Это подтверждённая потеря состава, а не необходимость изобретать ручку для каждого названия карточки.

Предлагаемый контракт расширения после согласования: `ranked?entity=artifact|route&metric=...&limit=5`, `breakdown?dimension=source|artifact_category|route_category|feedback_type`, `bars?dimension=device_class|screen_type|exit_step|feedback_channel`. Для нескольких нижних секций — конфигурация блоков с устойчивым section_id и явными запросами/возможностями; не выбирать первый и последний элемент массива по позиции. **Эти параметры пока не реализованы**. Поддерживаемые комбинации нужно перечислить в OpenAPI и capabilities; неизвестные/недоступные сочетания не игнорировать.

Истории и артефакты сейчас одна опубликованная сущность. Рекомендация v1: один источник и согласованные подписи; отдельная вкладка stories оправдана только другим аналитическим вопросом (чтение и завершение), а не дублированием артефактов с другими готовыми цифрами. Коллекции и медиа — не взаимоисключающие типы контента: их нельзя складывать с историями и маршрутами в круговую диаграмму до определения единой классификации/деноминатора.

## 7. Фильтры, сравнения и состояния

| Контрол | Область действия | Правило |
|---|---|---|
| Период / диапазон | Вся страница «Посетители», все блоки выбранной Stats tab | Один канонический query для summary/chart/sources/list/rankings/CSV. На главной фиксированный monthly summary — явно обозначенное исключение текущей версии |
| День/неделя/месяц/год | Calendar period по timezone музея | Сейчас period влияет на выбранный диапазон. Это не синоним группировки «по дням/неделям/месяцам» |
| from/to | Явный [from,to) | Либо обе границы, либо period. Одновременные period и from/to сейчас 400; клиент обязан убрать period при пользовательском диапазоне |
| timezone | Границы, подписи дат, сравнения и buckets | Сейчас default UTC; timezone браузера/методиста не является автоматически timezone музея. Сохранять явный выбор/настройку музея |
| Маршрут | Все связанные блоки при наличии route source | Фильтрует события/route runs данного маршрута, а не lifetime collection посетителей. Сейчас 400 filter_unavailable; контрол disabled с объяснением |
| Команда | Все связанные блоки при подтверждённом team membership | Сейчас недоступно. Нельзя доверять произвольному team_id из Visitor |
| Series | Только график | visitors/newVisitors или согласованная метрика. Не перезапрашивать все карточки только из-за серии |
| Сортировка / страница | Только таблица | page=1 при смене фильтров/сортировки; не менять summary; stable secondary id |

Новые фильтры предлагать через capabilities. Сейчас `GET /analytics/filter-options` возвращает periods, пустые routes/teams, route_filter=false, team_filter=false; нужна детализация доступности блоков/метрик, сортировок и dimension, не только общая boolean. Неподдержанный фильтр — ошибка или недоступный контрол, а не молчаливое игнорирование.

Текущая группировка backend: day/week/month — суточные buckets, year — месячные. Поэтому «День» сейчас даёт одну точку. Предложение: явный `bucket=hour|day|week|month` с hourly для day и дневными для week/month, monthly для year; это расширение backend, не текущая возможность. В DST-день возвращать фактические интервалы 23/25 часов с UTC offset, без склеивания одинакового локального часа. На фронтенде строить подписи из buckets, не индексами демо.

Сравнение сейчас: предыдущий полный календарный период; для явных дат — предыдущий равный по длительности интервал. Это может сравнивать неполный текущий месяц с целым прошлым. Рекомендация для оперативной аналитики — сравнение на одинаковую прошедшую часть периода; до согласования сохранить существующее правило и явно писать обе границы. Разница count/time: проценты или абсолютная единица с явной unit. Разница долей/рейтинга: процентные пункты/баллы. При предыдущем значении 0 — delta=null, не Infinity и не искусственный +100%.

Состояния каждого блока: loading (стабильное место и aria-busy), success, empty, source_unavailable, transport/auth error, stale. Ноль, null, пустой массив и 503 различаются. Повтор обновляет только блок. При смене фильтра старое значение не выдаётся за новое: abort/request key (museum,tab,range,timezone,filters) и проверка последнего ответа. После logout/смены музея очищать данные/кеш старого контекста.

Нет истории до включения сбора: нужны `collection_started_at`, coverage и состояние сборщика. `data_through` сейчас равно времени запроса, а не гарантированному watermark входных событий; для offline-событий данные прошлых интервалов могут уточняться. Убрать обещание макета «обновляется ежедневно в 00:00 МСК»: текущий backend читает таблицу сразу, timezone музея ещё не задана.

## 8. API-инвентарь и минимальный общий контракт

Внешние адреса на стенде: dashboard base `/api/dashboard/api/v1`, analytics base `/api/analytics/api/v1`. В сервисах маршруты начинаются с `/api/v1`; Caddy снимает только `/api/dashboard` или `/api/analytics`. Не терять и не удваивать API prefix. Не использовать localhost в production Visitor.

| Группа ручек | Что уже есть в коде | Что осталось |
|---|---|---|
| POST /analytics/events | Приём ограниченного v1 события, schema/size validation, resolve public_code, дедупликация, сохранение | Доказать сквозную доставку на стенде; измерение покрытия, расширения для новых метрик только после контракта |
| GET /analytics/filter-options | period/range validation, periods/routes/teams/capabilities | Детализация по метрике/блоку/sort и источники маршрутов/команд |
| GET /visitors/summary | total_visitors,new_visitors,avg_session_minutes,deltas,meta | Поле согласованных views/opens, returning и availability пустых средних |
| GET /visitors/dynamics | visitors/newVisitors, labels,values,buckets,meta | Согласованная hourly группировка; полный OpenAPI параметров |
| GET /visitors/sources | qr/direct/route/unknown,count,percent | UI должен передать общий диапазон; не считать social/referral без атрибуции |
| GET /visitors/list | items,total,page,limit; anonymous id/name, first_visit_at,duration_minutes,viewed_screens; route/collection null | Соответствие отображения nullable, полный экспорт, нужные источники для отключённых колонок |
| GET /stats/{tab}/summary, /chart | Visitors или screen_views в зависимости от tab | Карточки по матрице раздела 6, единицы, семантика views/opens |
| GET /stats/{tab}/ranked | Рейтинг artifact_id по screen_views | Реальные title/категория/version из каталога; entity selector, TOP limit и разные наборы секций |
| GET /stats/{tab}/breakdown, /bars | Отдают source_unavailable | Источники dimension; часть sources можно переиспользовать без новой таблицы |
| GET /dashboard/summary, /attendance | Проекция monthly visitors и dynamics; остальные summary поля null | Отображение доступности; согласованный период при расширении |
| GET /dashboard/recent-activity | В ходе проверки добавлена проекция GET /analytics/recent-activity по событиям Visitor | Согласовать заголовок и бизнес-смысл; это не журнал операций методиста |
| GET /dashboard/popular-routes, /feedback | Отдают source_unavailable | Route run/feedback sources; не заменять произвольными событиями просмотров |

Новые ручки нужны только там, где данных/операции действительно нет: источник серверных route run/feedback/collect integrations и экспорт всего множества. Имеющиеся клиентские пути сохранять, расширяя документированно; не создавать параллельный `/analytics/dashboard` для тех же метрик.

**Предлагаемый экспорт:** GET `/visitors/export.csv` с теми же фильтрами и сортировкой, без page/limit; серверный scope музея, объявленный лимит/поток и защита CSV-формул в текстовых полях. Для больших объёмов — отдельная job model после оценки нагрузки. `/stats/{tab}/export.csv` нужен лишь если требуется единый серверный отчёт; для показанных агрегатов допустим клиентский экспорт только актуального подтверждённого snapshot с фильтрами и units. Эти export endpoints пока отсутствуют.

Чтение методиста: Bearer, museum scope из проверенной сессии/claims, существующая проверка отзыва сессии. 401 → повторный вход, 403 → нет доступа, 400 → ошибка/недоступный фильтр, 503 → источник/сервис недоступен. Формат ошибки уже nested: `{error:{code,message}}`. Обработчик api.js должен извлекать `error.code/message`, а не сохранять объект error как строковый code.

Минимальный успешный ответ (пример предлагаемого расширения, не обещание текущего JSON):

```json
{
  "total_visitors": 2,
  "new_visitors": 1,
  "avg_session_minutes": 1.5,
  "screen_views": 3,
  "artifact_opens": 2,
  "availability": {"collected_artifacts": "source_unavailable"},
  "meta": {
    "from": "2026-10-17T00:00:00Z",
    "to": "2026-10-18T00:00:00Z",
    "timezone": "UTC",
    "filters": {"route_id": null, "team_id": null},
    "generated_at": "2026-10-17T12:00:00Z",
    "collection_started_at": "2026-10-01T00:00:00Z",
    "capabilities": {"route_filter": false, "team_filter": false}
  }
}
```

OpenAPI текущей реализации покрывает часть путей общими описаниями; требуется перечислить все поддержанные tab/view, полные схемы ответов, nullable, фильтры и ошибки на каждом методе. Документировать unavailable комбинации, а не подразумевать 7×5 полностью работающих методов.

## 9. Visitor: что собирать и как использовать

| Факт | Где | Контекст и применение |
|---|---|---|
| visit_start | Успешно открытый опубликованный контент, обычный story и /exhibits/{code} | museum проверяется через publication; session_id/visitor_key; first-entry source для уникальных/источников |
| scene_view | Фактическая видимость конкретного screen | public_code,artifact_id,screen_id; unique key; screen_views и derived artifact_opens |
| engagement | Видимый screen, интервалы до 15 сек, финальный остаток при hide/unmount | active_ms; активное время. Никаких фоновых heartbeat скрытой вкладки |
| scene_complete | Достигнут финальный экран | Текущий сигнал final, не доказательство полного чтения. Для полноценной воронки нужны run/version и критерий обязательных экранов |
| scan | Разрешившаяся публичная QR-ссылка | source — hint; отделить код физического сканера от URL-метки, если это нужно бизнесу |
| quiz_answer | Зафиксированный ответ | Только нужный correct boolean; не свободный текст/ФИО |
| collect | Успешная серверная запись artifacts-service | Надёжная интеграция persisted fact/outbox, без двойного клиентского и серверного счётчика |
| route / feedback / share / device | Пока не считать реализованным | Новые события/источники по контракту: route run и feedback серверные; share_action только действие; device_class — грубая категория, без fingerprint |

В отличие от предыдущей постановки, подключение PublicArtifactStory и дефолтного endpoint уже есть в коде. Обычные legacy вызовы track в use-visitor-data без public_code теперь могут возвращать null; нужно проверить, что актуальный StoryExperienceView покрывает каждый реальный вход, а не считать любой старый вызов доказательством доставки.

Очередь уже хранит стабильный event id, ждёт accepted_event_id, использует capped retry, отправляет beacon без удаления. Проверить reload/offline, повтор монтирования, два экрана и финал, повтор collect. События, созданные offline, должны получать корректную сессию, а время/дедупликация не должны меняться на retry. При отсутствии localStorage нельзя создавать нового visitor_key на каждый heartbeat: нужен хотя бы стабильный ключ на время вкладки; это требуется проверить отдельно.

Не добавлять посетителю новые формы/подтверждения/уведомления для обычного чтения. Для неизвестных сегментов оставлять unknown. Ошибка отправки не блокирует историю, QR, коллекцию или навигацию. Настройки приватности, если они существуют в продукте, должны соблюдаться.

## 10. Проверяемый пример данных

Изолированный музей M, диапазон R. У A есть visit до R; у B до R визитов нет. В R у A две сессии, у B одна. Приняты 90 секунд engagement A и 180 секунд B, итого 270 секунд на 3 сессии. Приняты screen_view A:S1, A:S2, B:S1 одного артефакта, повтор доставки A:S1 имеет прежний id. A открыл этот артефакт в одной сессии, вторую сессию создал допустимым visit_start без screen_view. Источники первого visit_start в R: A=qr, B=direct. У A один серверный collect и его retry. У B final одного story run; маршрутных фактов нет.

Ожидаемое: unique=2; new=1; returning=1/50%; sessions=3; avg_active=1.5 мин; screen_views=3; artifact_opens=2; sources qr=1/direct=1/50% каждый. После интеграции collect новые добавления=1; до неё поле unavailable. Final-story count=1, route_completed недоступно. Итог unique по графику может в сумме быть больше 2, если A пришёл в разные дни — это не ошибка, подпись должна объяснять дедупликацию по bucket.

Проверить также: visitor C другого музея не влияет; другой sort/page не меняет totals; ещё 60 посетителей доступны серверной пагинацией; пустой интервал не заменяется демо; интервалы на DST; from включительно/to исключительно; позднее событие меняет старый период документированно; 503 одного источника не превращается в 0; медленный ответ старого фильтра не перезаписывает новый; подписи/CSV имеют тот же диапазон и units.

## 11. Приоритет и последовательность поставки

1. **P1, данные v1:** проверить доступность сервисов отдельно от реализации; подключить уже существующие visitors summary/dynamics/sources/list с общим диапазоном, серверной пагинацией, состояниями без демо и корректными единицами. Стенд/развёртывание — отдельный владелец, в этом анализе не выполняется.
2. **P1, согласование смысла:** views против opens, время сессии против маршрута, stats summary/ranked по каждой вкладке, null/availability, источник/coverage, формат deltas. Нельзя «починить» отсутствующее поле artifact_views принудительным 0.
3. **P1, frontend slices после контракта:** посетители: загрузка/состояния; затем единые фильтры/пагинация; статистика: один согласованный overview; затем другие поддерживаемые вкладки. Не брать весь MP-006 как одну маленькую READY.
4. **P2, расширение источников:** маршруты/команды/коллекции/feedback/audit; затем соответствующие карточки, breakdown, дополнительные рейтинги и экспорт. Если эти функции обязательны для релиза, выпуск блокировать явно, не снижать полноту требования за счёт недоступных контролов.

Нужны решения владельца продукта/backend: (D1) v1 браузерная идентичность и future account link; (D2) одно значение открытия/завершения и роль версии контента; (D3) источник/модель маршрутов и команд; (D4) источник rating/feedback/audit; (D5) музейная timezone и сопоставимый период delta; (D6) какие неподдержанные вкладки разрешено временно отключить. Здесь даны рекомендации, но они не объявлены согласованным действующим контрактом.

Готовность: OpenAPI и METRICS совпадают с матрицей; хотя бы поддержанные блоки проходят fixture и e2e Visitor → persisted events → GET → три страницы; остальные имеют видимые причины недоступности. Рабочий endpoint, существующий код, успешный unit test и пользовательская готовность — четыре разные проверки.
