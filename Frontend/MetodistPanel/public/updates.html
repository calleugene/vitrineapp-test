MP-008P1

Защитить сохранение основных сведений от повторов и потери ввода

Статус
READY; добавлено 2026-10-17. Небольшой фронтенд-срез шага «создание артефакта → контент».
Проблема
во время POST/PATCH основных сведений можно продолжить менять название/описание и повторно нажать «К контенту» или загрузить обложку. Успешный ответ заменяет draft старым отправленным значением и снимает dirty; введённый во время ожидания текст пропадает. Для нового артефакта повторный вызов save до завершения первого отправляет ещё один POST и создаёт лишний черновик.
Доказательства
Frontend/MetodistPanel/src/features/artifacts/server-artifact-flow.jsx — Basic не передаёт disabled в TextInput/TextArea и footer «К контенту», Cover не учитывает flow.loading; Header блокирует свои кнопки, но не эти элементы. src/app/use-server-artifact-flow.js — save не проверяет выполняющееся сохранение, выбирает create при artifact=null, затем безусловно заменяет draft ответом и устанавливает dirty=false; uploadCover при отсутствии artifact также вызывает save. Backend/artifacts-service/internal/artifacts/service.go — CreateArtifact создаёт новый ID/PublicCode при каждом вызове. Дефект подтверждён последовательностью кода, без браузерного воспроизведения; network/скорость двойного клика не измерялись.
Объём
только сохранение Basic и связанные точки входа: синхронно исключить параллельные save и повторную навигацию до завершения текущего сохранения; на время операции заблокировать поля, footer и загрузку обложки с понятным ожиданием. Освобождать защиту при success/failure/ошибке валидации. Не менять API, другие редакторы и глобальную навигацию. Потерянный ответ POST и серверная идемпотентность вне этого среза.
Приёмка
deferred POST/PATCH удерживает исходный ввод и запрещает его изменение до ответа; кнопка «К контенту» показывает ожидание, повторное действие и конкурирующая загрузка обложки не создают второй запрос. Два синхронных вызова обработчика до React rerender дают один save и не более одного перехода. При успехе переход показывает именно сохранённые сведения; при network/401/500 остаются введённые значения, видна ошибка, блокировка снимается, повтор доступен. Ошибка валидации не оставляет форму заблокированной. Существующий сценарий загрузки обложки нового артефакта после сохранения работает.
Unit-тесты
тест фактического save/навигационного обработчика с управляемым promise и API spy: create и update, два синхронных вызова, повтор footer/обложки во время ожидания, один запрос и один переход; reject и повтор с исходным payload; ошибка валидации снимает guard. Проверить disabled/loading полей/footer/Cover на уровне компонента либо минимального используемого ими обработчика с отдельной проверкой привязки UI; один тест изолированного флага недостаточен. npm test, lint, typecheck, build и сценарий медленного ответа.
Риски и зависимости
не допустить взаимной блокировки uploadCover → save и не обещать безопасный автоматический повтор POST после потерянного ответа. Не сбрасывать ввод при отказе API. MP-003/MP-004 защищают локальный редактор экрана, а эта задача — основные сведения и создание артефакта; дубликата нет. Контракт CreateArtifact/UpdateArtifact подтверждён кодом, backend менять не требуется. MP-002 закрыта по контрактным/интеграционным тестам; браузерный стендовый прогон остаётся отдельным ограничением проверки.

MP-006P1

Подключить реальные данные и фильтры трёх страниц

Статус
BLOCKED; добавлено 2026-10-17 по прямому запросу пользователя. Требование распространяется на главную, «Посетителей» и «Статистику»: показатели и графики должны отражать бекенд и выбранные фильтры.
Проблема
вызовы API уже написаны, но не доказывают наличие реальных агрегатов. «Посетители» стартуют с VISITOR_STATS/VISITOR_ROWS, при ошибках сохраняют подставные данные; выбор дат, маршрута, команды и кнопка «Фильтры» не подключены. Запрашивается лишь первая страница из 50 строк, затем сортировка и пагинация работают по этому ограниченному набору. В «Статистике» ошибки и даже пустые успешные результаты подменяются демо; period передаётся только summary/chart, остальные блоки остаются без него. Есть риск показа старого ответа при быстрой смене периода.
Доказательства
Frontend/MetodistPanel/src/features/visitors/views.jsx — demo fallback, общий диапазон не передаётся sources/list, page=1/limit=50, неподключённые дата/route/team, null и потеря id; src/features/stats/use-stats-data.js, mappers.js, views.jsx — demo, устаревшие ответы, неполный period и первый/последний lowerSections; src/api.js — текущие query и поля. Новые backend sources присутствуют: analytics visitors summary не содержит artifact_views, stats summary отдаёт лишь одну метрику. Главная уже исправлена MP-005; детали несовпадений — PRODUCT_ANALYTICS_ANALYSIS.md.
Блокер и конкретный вопрос
владельцу бекенда предоставить актуальные исходники или контракт и доступный тестовый API dashboard/analytics; подтвердить, какие endpoints считают данные из реальных событий Visitor, как задаётся музей из авторизации, временная зона и границы day/week/month/year/диапазона, доступные фильтры маршрута/команды, допустимые sort_by/sort_dir, структура total/page/limit, семантика нулей/пустых результатов/дельт. Поддерживаются ли одинаковые фильтры агрегатами, графиками, списком и экспортом? Не считать URL из клиентского api.js подтверждённым контрактом; не придумывать параметры.
Объём после решения
разбить подключение на небольшие фронтенд-задачи по страницам; главную завершить поверх MP-005. Убрать статистические демо и fallback из «Посетителей»/«Статистики», ввести loading/empty/error/retry. Подключить согласованные фильтры ко всем относящимся к ним блокам, серверную пагинацию и сортировку списка; сбрасывать страницу при изменении фильтра, игнорировать устаревшие ответы. Несогласованные элементы фильтрации не оставлять выглядящими рабочими. Экспорт должен соответствовать выбранным фильтрам и явно обозначенному объёму данных.
Приёмка после снятия блокера
на тестовых событиях двух музеев цифры совпадают с серверными ответами и не смешиваются между музеями; выбранные период, даты, маршрут и команда реально меняют запросы и результат в пределах подтверждённой поддержки. На главной нет локальных рядов периода; в «Посетителях» доступны записи за пределами первых 50 с корректным total; в «Статистике» все связанные блоки относятся к выбранному периоду. Медленный старый ответ не перезаписывает новый. При нуле показывается ноль/пустое состояние, при сбое — ошибка, без демо в UI и CSV. Проверить сценарий событие Visitor → серверный агрегат → панель; демо и моки не подтверждают эту интеграцию.
Unit-тесты после решения
параметры каждого согласованного фильтра и сортировки по контракту; смена фильтра сбрасывает page; total > 50 и переход на последнюю страницу; deferred ответы A/B в обратном порядке; пустой ответ/нулевые значения/401/network/500/retry и частичный отказ; экспорт использует текущие фильтры и не содержит демо. Тестировать фактические обработчики и запросы, отдельно от интеграционной проверки серверных агрегатов.
Риски и зависимости
Реализованный v1 позволяет выделять небольшие фронтенд-срезы после согласования конкретных полей; не требуется ждать всех будущих route/feedback источников ради пустых/ошибочных состояний. Однако общий MP-006 остаётся BLOCKED до согласования матрицы и ограничения релиза. Новые browser identifiers не равны людям, null не равен 0; avg_session_minutes не равен времени маршрута. MP-005 и другие DONE сохраняются. Изменения backend/frontend идут параллельно — перед разработкой повторно сверять контракт и готовность стенда.

При сбое GET после PATCH данные могли уже сохраниться на сервере; повтор PATCH может увеличить draft revision — нельзя обещать откат или повторять запрос автоматически. MP-001P0

Не показывать «создать музей» при сбое загрузки профиля

Проблема
после входа ошибка museumApi.getProfile() теряется в Promise.allSettled, профиль остаётся пустым, и экран предлагает создать музей. Пользователь не видит разницы между отсутствием музея и ошибкой сети/доступа.
Доказательства
src/app/use-dashboard-data.js применяет профиль только при fulfilled; src/features/museum/views.jsx выбирает пустое состояние по !museumProfile.code. Бекенд возвращает ErrNotFound для отсутствующего профиля в Backend/artifacts-service/internal/artifacts/repository_sqlite.go; обработчик GET /museums/profile находится в Backend/artifacts-service/internal/artifacts/handler.go.
Объём
разделить состояния загрузки, 404 и остальных ошибок профиля музея; дать повторить загрузку при сбое. Не менять контракт создания музея и не подставлять демо-профиль.
Приёмка
404 показывает создание музея; 401/сбой сети/5xx показывают понятную ошибку и повтор; пока ответ не получен, кнопка создания не появляется; успешно загруженный профиль показывается как существующий. Остальные разделы продолжают загружаться при частичном сбое.
Unit-тесты
проверить классификацию ответов и выбор состояния экрана для 404, 401, сетевой ошибки и успеха. Добавить минимальный тестовый запуск, если инфраструктуры ещё нет.
Риск
не перепутать ответ 404 с 401; сохранить независимую загрузку остальных данных.
Уточнение 2026-10-17
READY; дефект по-прежнему подтверждён в текущем рабочем дереве. src/features/museum/use-museum-profile.js инициализирует пустой профиль, ошибка там относится только к сохранению. src/api.js сохраняет status HTTP-ошибки и code=service_unavailable при сетевом отказе. Backend/artifacts-service/internal/artifacts/handler.go (writeServiceError) переводит ErrNotFound в 404; middleware возвращает 401 до чтения профиля при неподходящем токене.
Уточнение объёма и приёмки
отдельные состояния loading/missing/loaded/error и повтор только GET профиля; создание доступно исключительно после 404. Повтор проходит через loading и приводит к loaded/missing либо снова error. Ошибку загрузки отделить от ошибки сохранения; не показывать старый профиль как успешно обновлённый после сбоя. Изменение только фронтенда, независимо от решения MP-002.
Уточнение unit-тестов
deferred promise не показывает создание; 404 показывает создание; 401/network/500 показывают ошибку без создания; повтор после ошибки приводит к успеху либо 404; отказ остальных API не мешает применить профиль, отказ профиля не теряет другие fulfilled-ответы. Проверить состояние экрана, не только классификатор. В package.json отсутствует test script: минимальный запуск входит в объём задачи.
Зависимости и проверка менеджера
MP-002 блокирует сквозной путь, но не эту обработку ошибок. Дубликата нет, критерии проверяемы; исходное уточнение менеджера основывалось на коде. Разработчиком дополнительно проверен браузерный сбойный сценарий; работающий API недоступен. История исходной постановки сохранена выше.
Результат
профиль имеет отдельные состояния загрузки, отсутствия, успеха и ошибки. Экран предлагает создание только после 404; при 401/сетевом сбое/5xx показывает ошибку и повторяет только GET профиля. Ошибка загрузки отделена от сохранения; загрузки остальных разделов остаются независимыми.
Проверки
npm test — 4/4; npm run lint, npm run typecheck, npm run build, git diff --check прошли. Локальный сценарий через mock-вход подтвердил сообщение об ошибке и кнопку повтора без предложения создать музей; повтор завершился той же ошибкой, потому что ArtifactsService недоступен.
Остаточный риск
интеграционный прогон с работающим ArtifactsService (ответы 404, 401 и 5xx) недоступен; классификация и UI-состояния покрыты unit-тестами. checkJs=false ограничивает typecheck JavaScript.
