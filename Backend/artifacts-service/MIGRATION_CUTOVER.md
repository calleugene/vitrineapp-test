# Перенос данных экспонатов в artifacts-service

Этот контур переносит данные из `exhibit-flow-service` без удаления исходной
базы и без смены UUID экспоната или уже напечатанного публичного кода. Он не
включает автоматическое переключение пользовательского трафика: это отдельное
решение после проверки отчёта.

## Границы безопасности

- `cmd/dbmigrate` работает только с PostgreSQL. Он блокирует параллельные
  запуски через advisory lock и фиксирует контрольную сумму каждой применённой
  миграции в `schema_migrations`.
- `cmd/legacy-exhibit-flow` читает исходную БД. Он не выполняет `DELETE`,
  `UPDATE` или DDL в `exhibit-flow-service`.
- Бинарные изображения не записываются в JSON и не теряются: перед импортом
  требуется `-asset-export-dir`. Файлы выгружаются в закрытый staging-каталог,
  проверяются SHA-256 и регистрируются со статусом `staged`. До загрузки этих
  файлов в объектное хранилище они не считаются готовыми для публикации.
- Откат в период переключения — возврат чтения и записи на legacy-сервис, а не
  удаление уже импортированных публикаций. Миграция `000001` специально не
  имеет разрушающего down-сценария.

## Целевая модель

Миграция добавляет, не заменяя существующие таблицы:

- `artifact_assets` и `artifact_asset_links` — ссылки на неизменяемые файлы;
- `artifact_content_screens` — контентные экраны `text`, `model`, `test`;
- `artifact_public_codes` — постоянный код/ссылка и сохранённые legacy-коды;
- `artifact_publications` — неизменяемые JSONB-снимки версий;
- `legacy_exhibit_import_map` и `legacy_exhibit_import_runs` — журнал
  соответствий и отчётов.

Новые канонические коды должны иметь не менее 128 бит криптографической
случайности. Код из legacy (`public_token`) переносится как `legacy_alias`,
чтобы существующий QR-код продолжал работать; он не становится основанием для
генерации новых кодов.

`museum_id` в новой прикладной логике должен поступать из проверенной сессии
или JWT, а не из заголовка клиента. До включения записи в новые таблицы нужно
включить RLS и выполнять `SET LOCAL app.museum_id` в каждой транзакции. Публичное
разрешение кода должно выполняться отдельным ограниченным путём, который
возвращает только активную опубликованную версию.

## Порядок запуска

1. Сделайте резервные копии обеих PostgreSQL БД и зафиксируйте число
   `exhibits`, `screens`, `publications` по музеям.
2. Примените только additive-схему:

   ```bash
   cd Backend/artifacts-service
   go run ./cmd/dbmigrate -dsn "$ARTIFACTS_DB_DSN" -status
   go run ./cmd/dbmigrate -dsn "$ARTIFACTS_DB_DSN"
   ```

3. Сначала запустите сверку. Код возврата `2` означает несовпадения и не
   является разрешением на переключение:

   ```bash
   go run ./cmd/legacy-exhibit-flow \
     -mode check \
     -source-dsn "$LEGACY_EXHIBIT_FLOW_DSN" \
     -target-dsn "$ARTIFACTS_DB_DSN"
   ```

4. Выполните импорт с защищённым staging-каталогом. Повторный запуск безопасен:
   UUID, коды и снимки вставляются только один раз, а существующие записи
   сравниваются с источником.

   ```bash
   go run ./cmd/legacy-exhibit-flow \
     -mode import \
     -source-dsn "$LEGACY_EXHIBIT_FLOW_DSN" \
     -target-dsn "$ARTIFACTS_DB_DSN" \
     -asset-export-dir /secure/staging/exhibit-flow-assets
   ```

5. Повторите режим `check`. В JSON-отчёте должны быть нулевые
   `mismatches`; сверьте также хеши и число строк из
   `legacy_exhibit_import_runs`.
6. Загрузите staged-файлы в объектное хранилище, проверьте хеши, смените их
   состояние на `ready` отдельной проверенной операцией. Затем в окне
   обслуживания остановите legacy-запись, прогоните финальный импорт,
   переключите флаг чтения на artifacts-service и наблюдайте ошибки/QR-резолв.

## Что не удалять сейчас

Не удаляйте `exhibit-flow-service`, его PostgreSQL-таблицы, SQLite-файлы,
старые public tokens, `media`, `models`, `drafts` или поля старого `artifacts`
до завершения согласованного срока отката и проверки внешних потребителей.
После срока отката удаление делается отдельной миграцией с резервной копией и
явным подтверждением: текущая миграция намеренно только добавляет данные.
