# Микросервисы Витрины

Реализованы и подключены route-service (8083), feedback-service (8086), notification-service (8087). В Windows они слушают только 127.0.0.1:18083/18086/18087 и доступны через /api/route, /api/feedback, /api/notification. Dashboard и Analytics используют эти сервисы как источники; репозиторий больше не требует отсутствующего museum-service — профиль музея и каталог находятся в artifacts-service.

## Запуск Windows

Build.ps1 собирает все восемь сервисов. Start.ps1 создаёт недостающие базы vitrine_route, vitrine_feedback, vitrine_notification, выполняет идемпотентную инициализацию схем и запускает сервисы. После изменения Caddyfile нужен reload Caddy или перезапуск. Status.ps1 проверяет readiness всех API; Check.ps1 включает новые сервисы в восстановление; Stop.ps1 их останавливает; Backup.ps1 сохраняет новые базы. Старые установки могут сделать резервную копию до появления новых баз.

## Развёртывание Linux / Selectel

1. Установить Docker Engine с Compose plugin на Linux-сервере.
2. Скопировать deploy/compose.env.example в .env в корне репозитория и задать случайный POSTGRES_PASSWORD без URL-спецсимволов (например, hex), AUTH_TOKEN_SECRET не короче 32 байт, PUBLIC_URL и SITE_ADDRESS. Для восстановления пароля настроить SMTP. Секреты не отправлять во frontend.
3. Запустить `docker compose up -d --build`. Корневой compose содержит только существующие сервисы, PostgreSQL и Caddy с обеими собранными страницами. Снаружи опубликованы только 80/443, базы и внутренние API остаются в сети Compose.
4. Направить DNS домена на публичный IP сервера и открыть 80/443 для получения сертификата Caddy.
5. Перед переносом реальных данных сделать согласованный backup PostgreSQL и загруженных файлов. На существующем Docker volume init-скрипт PostgreSQL повторно не запускается: недостающие базы нужно создать перед стартом новых сервисов. Создание пустой базы не переносит данные Windows.

В этой работе проверены Compose config и синтаксис Caddy; Docker Engine на рабочем компьютере не запущен, поэтому контейнерная сборка/запуск здесь не подтверждены. Нативные Windows-сервисы запущены и проверены с PostgreSQL. Linux-бинарники проверяются отдельной кросс-компиляцией.

## Доступ и хранение

Общая библиотека Backend/platform используется тремя отдельными исполняемыми сервисами. Каждый имеет собственную PostgreSQL-базу, не записывает данные в чужую базу и может развёртываться отдельно. SQLite поддерживается для быстрых тестов. Профиль музея остаётся в Artifacts; отдельный пустой MuseumService не создаётся.

Чтение и изменение данных методиста требует Bearer-токен Auth. Сервис проверяет подпись, срок, роль и актуальную сессию/членство через /auth/authorize-museum. Переданные X-Museum-ID и museum_id не заменяют подписанный контекст. Для Visitor проверяется /auth/me и активность аккаунта. X-User-ID не используется как авторизация уведомлений.

Начальная схема records/events/source_cursors/notification_reads создаётся при старте через CREATE IF NOT EXISTS. Каждое изменение объекта и его событие записываются одной транзакцией. Объекты имеют version; конфликт устаревшей записи возвращает 409. Поле version можно передавать в PATCH/ответах; панель передаёт его для ответов и модерации. Форматы JSON и индексы одинаковы в PostgreSQL и SQLite. Сервер ограничивает JSON, задаёт HTTP timeouts, корректно завершает работу при SIGTERM. Ошибки имеют вид {error:{code,message}}.

## Маршруты

- GET/POST /api/v1/routes — список с пагинацией/фильтром status/search и создание.
- GET/PATCH/DELETE /api/v1/routes/{id} — чтение, изменение, архивирование с отключением публичного доступа. Физическое удаление не стирает историю прохождений.
- POST /routes/{id}/artifacts, DELETE /routes/{id}/artifacts/{artifact}, PUT /routes/{id}/artifacts/reorder — атомарное изменение порядка. Повторы ID, чужие экспонаты и некорректная перестановка отклоняются.
- GET /routes/summary, /routes/recent-activity, /routes/popular, /routes/metrics — реальные сводки и события. Popular/metrics на главной относятся ко всему времени, что подписано в UI; средняя длительность считается только по завершённым сессиям.
- GET /public/museums/{museum}/routes, GET /public/routes/{id} — только опубликованные публичные маршруты. Публикация требует хотя бы один опубликованный экспонат того же музея.
- POST /public/routes/{id}/start и /progress — visitor_key, session_id, для progress также artifact_id. Ключ начала детерминированный: повтор не создаёт вторую сессию. Состав маршрута фиксируется на старте и не меняет уже начатое прохождение после редактирования маршрута.
- Progress проверяет сохранённый факт коллекции в Artifacts через ROUTE_ARTIFACTS_DB_DSN. Нажатия без сохранённой коллекции не завершают маршрут; недоступный источник даёт 503, неподтверждённый факт — 409. Завершение фиксируется единожды.

Visitor показывает маршруты в музее и по /routes/{id}, открывает экспонаты по порядку, сохраняет прогресс после подтверждённого collect. QR-ссылки добавляют source=qr. При require_qr новая сессия требует этот маркер; это подсказка источника, не доказательство физического сканирования и не средство аутентификации. visitor_key — браузерный псевдоним, не проверенная личность. Карта маршрутов пока недоступна, соответствующий переключатель выключен.

## Обратная связь

- POST /api/v1/public/feedback — активный аккаунт Visitor, клиентский id для идемпотентности, public_code, type (review/question/suggestion), title, body, rating (1–5 только для review). Музей и экспонат определяются по действующей публичной публикации; автор — по аккаунту. Повтор того же id с изменённым содержимым даёт 409. Ограничение — десять новых сообщений на аккаунт в час (базовый контроль нагрузки).
- GET /feedback и /feedback/{id} — только свой музей, фильтры type/status/reply_status, пагинация.
- PUT /feedback/{id}/reply — body, status (draft/published), version. Имя сотрудника определяется сервером.
- PATCH /feedback/{id} — модерация pending/published/rejected. Публичными могут быть только отзывы.
- GET /feedback/summary — оценка только по опубликованным отзывам; если их нет, rating=null.
- GET /public/museums/{museum}/reviews — опубликованные отзывы без приватных идентификаторов аккаунта и черновиков ответов.
- GET /public/feedback/{id} — собственное сообщение Visitor; черновик ответа скрыт.

Форма Visitor доступна из истории экспоната. Для отправки нужно войти в аккаунт посетителя в основном приложении. Панель загружает реальные сообщения, сохраняет ответы, публикует/скрывает отзывы. Пустой ответ API не превращается в демонстрационные сообщения.

## Уведомления

GET /api/v1/notifications, POST /notifications/{id}/read, POST /notifications/read-all. Непрочитанные состояния персональные, принадлежат пользователю из токена и не влияют на коллег.

Источник — долговечный журнал событий Route/Feedback, записанный в той же транзакции, что изменение. При чтении Notification подтягивает события через авторизованный /api/v1/events, сохраняет их с уникальным ID и обновляет cursor транзакционно. Повторная доставка не дублирует уведомления. Есть перекрытие окна на минуту для коротких транзакций, завершившихся не по порядку. Если источник не отвечает, возвращается сохранённый список с unavailable_sources; успешный пустой результат не подменяется демо. Обновление происходит при запросе списка/открытии меню, без WebSocket и push/email-рассылок. Артефакты пока не являются источником уведомлений.

## Статистика

Analytics проксирует /stats/routes/{summary,chart,breakdown,ranked,bars} и /stats/feedback/... в соответствующие сервисы. Обе цепочки используют один выбранный период, диапазон [from,to) и timezone (UTC по умолчанию); интервалы ограничены 367 днями. Бакеты — календарные дни с учётом DST. Маршрутная статистика строится по сессиям, начатым в диапазоне, завершения учитываются до конца диапазона. Feedback — сообщения, созданные в диапазоне; опубликованность отзыва оценивается на момент запроса. Метаданные содержат точные границы.

Командный каталог и фильтры посетителей по route/team не реализованы: события истории ещё не содержат проверенного route-контекста. Они не имитируются. Весь путь поиска/просмотра всех ответов Visitor, уведомления из Artifacts, медиа в ответах и карта — отдельные расширения интерфейса.

## Проверки

- Backend/platform: тесты жизненного цикла маршрута, чужого музея, порядка, version conflict, идемпотентного начала, подтверждения коллекции, снимка маршрута, DST, отзыва/модерации/черновика ответа, дедупликации уведомлений, персонального прочтения и восстановления после перезапуска; go vet.
- Analytics: тесты проксирования новых источников, сохранения Bearer и единого диапазона; прежние тесты аналитики.
- Dashboard: источники маршрутов/отзывов, реальная оценка и корректные ошибки.
- Панель: lint/typecheck/build и unit tests, включая сохранение Bearer/X-Museum-ID при JSON-мутациях. Visitor: lint/typecheck/smoke/build.
- deploy/windows/Smoke-Services.ps1: реальные Auth, Artifacts, PostgreSQL, Route, Feedback, Notification, Dashboard через Caddy. По умолчанию удаляет только собственные fixture-данные с уникальным marker; -KeepData оставляет их для UI-проверки. Использует существующий локальный тестовый аккаунт и опубликованный тестовый экспонат из ignored .runtime. Не запускать на произвольной production-инсталляции.
- В браузере проверены вход методиста, список маршрутов, переход из публичного маршрута в историю, форма обратной связи, серверная вкладка статистики маршрутов и сохранение ответа музея через интерфейс.
