# Микросервис сценария добавления экспоната

Автономный сервис реализует только девять согласованных экранов: основные сведения и обложка, состояния контента, текстовый экран, публикация и QR-ссылка.

## Запуск

```bash
cd Backend/exhibit-flow-service
docker compose up --build
```

Откройте `http://localhost:8091`. Основная база сервиса — PostgreSQL 16. Контейнер создаёт базу `exhibit_flow`, применяет схему при старте сервиса и сохраняет данные в именованном Docker-томе.

Для подключения к уже существующему PostgreSQL задайте `EXHIBIT_FLOW_DB_DSN`, например: `postgres://user:password@host:5432/exhibit_flow?sslmode=disable`.

Для QR-кодов в рабочем окружении задайте внешний адрес сервиса: `EXHIBIT_FLOW_PUBLIC_BASE_URL=https://museum.example`. Без него сервис использует адрес входящего запроса; локально это `http://localhost:8091`.

## Проверка девяти состояний

1. Откройте страницу: отобразится выбор экспоната.
2. Через `⋮` у карточки можно дублировать или удалить экспонат. Правая кнопка `↗` открывает его опубликованный просмотр.
3. Нажмите «Добавить экспонат», заполните название и краткое описание.
4. Загрузите JPG, PNG или WebP размером до 10 МБ: появится состояние с обложкой.
5. Перейдите на вкладку «Контент». Если сведения изменились, они сохранятся автоматически. До добавления экранов будет пустое состояние.
6. Для состояния недоступного сервиса откройте `http://localhost:8091/?content=error`.
7. Нажмите «Добавить», затем выберите «Текст».
8. Заполните редактор и сохраните: в списке появится экран. Перетащите его за маркер `⠿`; через `⋮` доступны дублирование и удаление.
9. Нажмите «Опубликовать»: появятся постоянная ссылка и QR-код для нового экспоната. После первой публикации та же кнопка называется «Сохранить изменения» и создаёт новую опубликованную версию.
10. Откройте ссылку вида `/exhibits/AB00Z`: появится мобильный просмотрщик экранов. Измените текст или сведения и нажмите «Сохранить изменения»: отобразится сообщение об обновлении. Проверить неизменяемость версии можно по `GET /api/v1/public/exhibits/{code}`.

После JSON-запроса адрес страницы получает `exhibit_id`, а также безопасную отладочную отметку `request=redacted` и размер тела. Текст и другие данные запроса не попадают в URL, историю браузера, журналы прокси и Referer. Загрузка файлов также не попадает в адресную строку: её тело двоичное и может быть до 10 МБ.

## HTTP API

В Docker-демо включён `EXHIBIT_FLOW_DEMO_MODE=true`, поэтому тестовая страница работает без входа. В рабочем запуске выключите этот режим и задайте `EXHIBIT_FLOW_MUSEUM_TOKENS` в формате `museum_id:token,museum_id:token`. Каждый защищённый запрос передаёт `Authorization: Bearer <token>`; идентификатор музея из браузерного заголовка не принимается.

- `POST /api/v1/exhibits` — создать экспонат.
- `GET`, `PATCH /api/v1/exhibits/{id}` — прочитать или изменить сведения.
- `POST`, `DELETE /api/v1/exhibits/{id}/cover` — установить или убрать обложку.
- `GET`, `POST /api/v1/exhibits/{id}/screens` — список и создание текстовых экранов.
- `GET`, `PATCH`, `DELETE /api/v1/exhibits/{id}/screens/{screenId}` — работа с экраном.
- `POST /api/v1/exhibits/{id}/screens/order` — изменить порядок.
- `POST /api/v1/exhibits/{id}/publish` — создать неизменяемую опубликованную версию.
- `GET /api/v1/exhibits/{id}/qr.png` — получить PNG QR-кода опубликованной публичной ссылки.
- `GET /exhibits/{code}` — открыть публичный просмотрщик в формате stories без авторизации. `code` — пять случайных символов `A-Z0-9`.
- `GET /api/v1/public/exhibits/{code}` — получить последнюю опубликованную JSON-версию для мобильного клиента.

## Рекомендуемая JSON-модель

Не стоит хранить файлы внутри JSON экспоната: в рабочем контуре изображения и 3D-файлы должны лежать в объектном хранилище, а JSON содержит ссылки на версии файлов. JSON полезен как неизменяемый снимок при публикации и как контракт мобильного клиента.

```json
{
  "schema_version": 1,
  "id": "exh_01J...",
  "museum_id": "museum_01J...",
  "metadata": {
    "title": "Крылатая фигура",
    "short_description": "Экспонат начала XX века",
    "cover_asset_id": "asset_01J..."
  },
  "lifecycle": {
    "status": "draft",
    "updated_at": "2026-09-14T12:00:00Z",
    "published_version": 3,
    "public_code": "AB00Z"
  },
  "screens": [
    {
      "id": "screen_01J...",
      "position": 1,
      "kind": "text",
      "content": {
        "title": "История находки",
        "body": "Текст для посетителя",
        "image_asset_id": "asset_01J..."
      }
    },
    {
      "id": "screen_01K...",
      "position": 2,
      "kind": "model",
      "content": {
        "title": "Рассмотрите модель",
        "body": "Поверните объект пальцем",
        "model_asset_id": "asset_01K...",
        "poster_asset_id": "asset_01K..."
      }
    }
  ]
}
```

Для `kind: "test"` нужен отдельный объект `content` с вопросом, вариантами и правилами проверки; не смешивайте поля теста, текста и 3D-модели в одной плоской структуре. В базе данных это лучше хранить нормализованно (`exhibits`, `screens`, `assets`, `publications`), а JSON-снимок сохранять в `publications.snapshot_json` при каждой публикации.

## Проверка

```bash
go test -race ./...
go vet ./...
```

Тесты используют SQLite только в памяти: это изолированный быстрый контур, не подмена рабочей PostgreSQL-базы. При обычном запуске сервис принимает только PostgreSQL DSN, а миграция `001` учитывается в `schema_migrations` и выполняется под PostgreSQL advisory lock.
