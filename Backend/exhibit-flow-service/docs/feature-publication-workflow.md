# Функция: публикация только при наличии изменений

## Зачем нужна

У экспоната есть черновик для редактирования и опубликованная версия, которую видит посетитель по QR-коду. Функция исключает бессмысленную повторную публикацию: после публикации кнопка «Сохранить изменения» неактивна, пока сотрудник музея не внесёт новое изменение.

Ссылка вида `/exhibits/AB00Z` и соответствующий QR-код постоянны. При повторной публикации обновляется содержимое по этой ссылке, а не сама ссылка.

## Сценарий пользователя

1. Сотрудник создаёт экспонат. Главная кнопка активна и называется «Опубликовать».
2. После успешной публикации открывается вкладка «Публикация» со ссылкой и QR-кодом.
3. Главная кнопка меняется на «Сохранить изменения» и становится неактивной.
4. Пользователь меняет название, описание, обложку, добавляет, редактирует, удаляет, дублирует или меняет порядок экранов.
5. Кнопка «Сохранить изменения» становится активной.
6. Нажатие создаёт новую опубликованную версию, снова отключает кнопку и показывает актуальную публикацию.

Если пользователь вернул несохранённые поля к первоначальным значениям, кнопка снова отключается. Неудачный запрос не меняет состояние кнопки и показывает понятное сообщение об ошибке.

## Правила интерфейса

- До первой публикации доступна кнопка «Опубликовать».
- После первой публикации доступна только «Сохранить изменения» и только при наличии изменений.
- Вкладка «Публикация» заблокирована до первой успешной публикации.
- Заблокированная кнопка имеет не только другой цвет, но и `disabled`, подсказку «Сначала внесите изменения в экспонат» и не доступна с клавиатуры.
- Иконка «Назад» слева от заголовка возвращает к списку экспонатов.
- Состояние «есть неопубликованные изменения» сбрасывается только после успешного ответа сервера о публикации.

## Реализация на React

Хранить серверные данные отдельным источником состояния, например TanStack Query, а локальные поля формы — в React Hook Form. Не использовать только CSS-класс: блокировка должна быть вычислена из данных.

```ts
const published = exhibit.status === 'published' && exhibit.publications > 0;
const changedFields = !deepEqual(form.getValues(), savedDraft);
const canPublish = !published || changedFields || contentDirty;
```

`contentDirty` становится `true` после успешных операций с обложкой и экранами. После `POST /publish` нужно обновить кэш экспоната, записать новую версию и сбросить `contentDirty` в `false`. Для операций с экранами удобнее инвалидировать запросы `['exhibit', exhibitId]` и `['screens', exhibitId]`.

Перед уходом к списку нужно предупреждать об изменениях, которые ещё не сохранены в черновик. Это отдельное состояние от неопубликованных изменений: сохранённый черновик может отличаться от публичной версии.

## Серверная часть: Go и PostgreSQL

Сервер — единственный источник истины о публикации. Клиентская блокировка улучшает сценарий, но не является защитой от прямого вызова API.

### Модель данных

```sql
exhibits (
  id uuid primary key,
  museum_id uuid not null,
  public_code char(5) unique not null,
  status text not null check (status in ('draft', 'published')),
  draft_revision bigint not null default 1,
  published_revision bigint not null default 0,
  updated_at timestamptz not null
)

exhibit_publications (
  exhibit_id uuid not null,
  version bigint not null,
  snapshot jsonb not null,
  published_at timestamptz not null,
  primary key (exhibit_id, version)
)
```

`snapshot` содержит полный неизменяемый снимок экспоната и упорядоченных экранов. Файлы хранятся в объектном хранилище, а в снимке остаются их версионные URL и метаданные.

### Контракт API

- `GET /api/v1/exhibits/{id}` возвращает `draft_revision`, `published_revision`, `has_unpublished_changes`.
- Изменение сведений, обложки и экранов увеличивает `draft_revision` в транзакции.
- `POST /api/v1/exhibits/{id}/publish` принимает `expected_draft_revision`.
- При совпадении ревизий сервер создаёт новую запись публикации, ставит `published_revision = draft_revision` и возвращает версию, публичную ссылку и признак первой публикации.
- Если `draft_revision = published_revision`, сервер отвечает `409 no_unpublished_changes` и не создаёт пустую версию.
- При устаревшей версии сервер отвечает `409 revision_conflict`; интерфейс предлагает обновить данные, не затирая чужие изменения.

Операция публикации должна выполняться в одной транзакции PostgreSQL с блокировкой строки экспоната (`SELECT ... FOR UPDATE`). Это предотвращает две одновременные публикации одной и той же версии.

## Доступ и безопасность

- Все кабинетные запросы проверяют пользователя, музей и роль до чтения или изменения экспоната.
- Доступ к данным ограничивается `museum_id` на каждом запросе; идентификатор музея из браузера нельзя считать доверенным.
- Публичный маршрут `/exhibits/{public_code}` отдаёт только опубликованный снимок без служебных полей и без доступа к черновику.
- QR-код строится из публичного HTTPS-адреса; адрес задаётся конфигурацией окружения, а не заголовком клиента в рабочем окружении.
- URL не должен содержать тело запросов, токены или персональные данные.

## Проверка перед выпуском

- Черновик: «Опубликовать» активна.
- Опубликованный экспонат без изменений: «Сохранить изменения» выключена.
- Каждое из восьми типов изменений активирует кнопку: название, описание, обложка, добавление, редактирование, удаление, дублирование и перенос экрана.
- Ошибка изменения или публикации не активирует кнопку ошибочно и не меняет публичную версию.
- Повторная публикация меняет снимок, но сохраняет `public_code`, URL и QR-код.
- Два одновременных запроса на публикацию не создают две одинаковые версии.
- Проверка клавиатурой, экранным диктором и на ширинах 320, 768, 1024 и 1440 пикселей.
