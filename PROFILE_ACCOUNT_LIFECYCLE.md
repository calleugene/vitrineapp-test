# Профиль и жизненный цикл аккаунта

Страница `/user-profile` использует React 19 и существующий Gravity UI. Пять полей: имя, фамилия, email, телефон, «О себе». Форма отправляется явно, только при изменениях. Фото выбирается и сохраняется отдельно; сервер проверяет изображение JPG/PNG до 5 МБ и нормализует его в JPEG до 512 px. Успешное сохранение обновляет аватар в меню пользователя и показывает toast.

## Запуск

Изменения требуют обновления **AuthService, ArtifactsService, VisitorService, AnalyticsService и frontend**. Публичное окружение в рамках этой задачи не перезапускалось. Схема AuthService обновляется при старте через `InitSchema` для PostgreSQL и SQLite; существующие связи с единственным музеем переносятся в `museum_memberships`. Перед обновлением рабочего окружения используется обычная резервная копия базы.

AuthService:

- `AUTH_TOKEN_SECRET`: общий секрет с ArtifactsService, минимум 32 байта.
- `MUSEUM_SERVICE_URL`: адрес ArtifactsService с `/api/v1`.
- `AUTH_SMTP_ADDR`, `AUTH_MAIL_FROM`, `AUTH_SMTP_USER`, `AUTH_SMTP_PASSWORD`: существующие настройки SMTP. Подтверждение email использует STARTTLS и ограниченные сетевые таймауты.
- `AUTH_EXPOSE_DEBUG_TOKENS=false` в production. Без настроенной доставки запрос смены email возвращает 503; адрес не меняется и успешная отправка не имитируется.

ArtifactsService: `AUTH_SERVICE_URL` указывает на AuthService с `/api/v1`. Production entrypoint всегда задаёт его; отключение проверки возможно только через явную конфигурацию тестового `Service`. Проверка действующего аккаунта и музейной связи выполняется при каждом защищённом запросе, включая запросы со старым подписанным токеном. Недоступность AuthService запрещает операцию.

Docker Compose и Windows Start настроены на взаимные адреса сервисов. SMTP-реквизиты задаются окружением запуска, в репозитории их нет.

## API

Все маршруты ниже имеют префикс `/api/v1` и требуют текущую авторизацию, кроме уже существующих маршрутов входа.

| Метод и путь | Назначение |
| --- | --- |
| `GET /users/{userId}` | Профиль и серверные даты, авторизация self/admin |
| `PATCH /users/{userId}` | Имя, телефон и описание; произвольная смена email запрещена |
| `POST /users/{userId}/avatar` | Multipart `file`, отдельное сохранение фото |
| `POST /auth/email-change` | `{email}`, письмо с одноразовым токеном, срок 1 час |
| `POST /auth/email-change/confirm` | `{token}`, подтверждение нового адреса |
| `GET /users/{userId}/museums` | Подтверждённые связи, имена, логотипы и роли |
| `POST /auth/museums/select` | `{museum_id}`, проверка связи, обновление контекста и access token |
| `POST /auth/museums/join` | `{museum_id, code}`, серверная проверка пары ID/код и обновлённый список музеев |
| `POST /auth/museums/code` | Создание/перевыпуск кода для текущего музея владельцем/администратором |
| `DELETE /auth/museums/code` | Отзыв кодов текущего музея |
| `POST /auth/deactivate` | ACTIVE → DORMANT |
| `POST /auth/reactivate` | DORMANT → ACTIVE до срока удаления |
| `GET /auth/authorize-museum` | Проверка действующего аккаунта и связи для других сервисов |

Сервисные метаданные музея читаются через `GET /api/v1/internal/museums/{museumId}` с `X-Service-Secret`. Публичного доверия заголовку с ID музея нет. Внутренний контракт ArtifactsService содержит `museum_id`; пользовательский список возвращает `id` для навигации.

## Приглашения

Код — 256-битный криптографически случайный непрозрачный токен; в базе хранится только хеш и связь с музеем. Срок — 7 дней. Создание нового кода отзывает предыдущие. Уникальный ключ `(user_id, museum_id)` исключает дубли. Код проверяется в транзакции вместе с переданным ID музея; несовпадение не создаёт связь. Обычный присоединившийся сотрудник получает роль `methodist`, без права выпускать приглашения.

Проверки и счётчик находятся в транзакциях базы. Лимит — 5 попыток подключения за 15 минут на авторизованный аккаунт, общий для экземпляров сервиса. Ответы: 404 `code_not_found`, 410 `code_invalid`, 409 `already_joined`, 429 `join_rate_limited`. Смена email ограничена 3 запросами за 30 минут. Frontend показывает разные сообщения и не предоставляет доступ по проверке формата токена.

В верхней карточке боковой панели стрелка открывает меню реальных подключённых музеев. Меню и раздел «Мои музеи» используют общий серверный список; после подключения новый музей появляется в обоих местах. Выбор сначала получает проверенный сервером контекст и access token, затем обновляет данные кабинета и открывает профиль музея.

На странице музея владельцу/администратору доступен ID музея с копированием и карточка выпуска, копирования, отзыва и перевыпуска кода. Новый код показывается только после создания. Перезагрузка страницы не восстанавливает исходный секрет из его хеша.

## Деактивация, восстановление и данные

`deactivated_at` и `scheduled_deletion_at` устанавливает сервер. Срок равен 30 × 24 часа с момента деактивации. Повторная деактивация DORMANT не сдвигает срок. Вход и refresh не активируют аккаунт. После входа frontend проверяет серверный статус до показа кабинета и выводит отдельный экран восстановления.

Для DORMANT остаются вход, чтение собственного статуса через `/auth/me`, обновление сессии, выход и явная активация. Защищённые пользовательские и музейные операции запрещены. Восстановление после срока отклоняется сервером даже до следующего прохода задачи очистки.

AuthService запускает идемпотентную задачу при старте и каждую минуту. Для просроченных DORMANT она в транзакции:

1. Устанавливает DELETED и заменяет email техническим адресом tombstone.
2. Очищает имя, телефон, описание, фото, дополнительные персональные поля и пароль.
3. Удаляет сессии, токены, отложенные письма, пользовательскую активность, запросы смены email, лимиты подключения и связи с музеями.
4. Сохраняет неперсональный ключ tombstone и даты жизненного цикла для целостности ссылок. Записи подтверждённых согласий хранят версию документа и факт согласия по этому ключу без имени и email. Псевдонимные организационные ссылки и агрегированная аналитика не каскадируются.

Профили музеев, артефакты, опубликованные материалы, коллекции организации и доступ других сотрудников принадлежат организации. Их удаление не вызывается ни при деактивации, ни при удалении пользователя. Код не отправляет команды удаления в ArtifactsService. Личные данные во внешних резервных копиях подчиняются отдельному сроку хранения резервных копий инфраструктуры; задача не переписывает бэкапы.

## Проверка

- Frontend: `npm run check`, `npm test`.
- Go: `go test ./...` в AuthService, ArtifactsService, VisitorService и AnalyticsService.
- `profile_test.go`: переходы статусов, точная граница 30 дней, вход без восстановления, запрет API, очистка, коды/дубли/отзыв/лимиты, email и аватар.
- `profile_postgres_test.go`: миграции и операции PostgreSQL; требует `AUTH_PROFILE_TEST_DSN` на отдельную тестовую базу.
- `account_lifecycle_test.go`: старый токен не позволяет менять музей после деактивации; организационный профиль сохраняется.
- `scripts/profile-smoke.mjs`: браузерные сценарии на явно заданных тестовых ответах, desktop 1440 px и mobile 390 px, сохранение, фото в шапке, копирование ID, email, подключение, восстановление и переключение контекста. Требует Playwright и Edge (`PROFILE_BROWSER_CHANNEL` можно переопределить), адрес через `PROFILE_PREVIEW_URL`.
- `scripts/profile-backend-smoke.mjs`: 27 HTTP-запросов к реальным AuthService + ArtifactsService на изолированных PostgreSQL-базах. Требует явные `PROFILE_AUTH_QA_URL` и `PROFILE_ARTIFACTS_QA_URL`, а debug-токены допускаются только в этом тестовом окружении.

В браузерном тесте данные фиктивные и ограничены тестовым перехватчиком. В самой странице production-подстановок профиля и музеев нет. Отсутствующие даты отображаются как «Нет данных», все реальные даты форматируются часовым поясом браузера.
